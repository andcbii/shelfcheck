# Separate provider catalogue freshness from Plex comparisons

Every full Plex scan checks the library inventory for changes. Retain downloaded TMDB and TVDB catalogues independently of comparison results so a coverage mapping or ownership change can trigger a new comparison without downloading otherwise reusable provider data. Saving, editing, or deleting Manual Matches, including bulk deletion, immediately rechecks only affected shows using saved catalogues and available saved library inventory. Include shows affected by both old and new members, and mark all affected shows for fresh provider downloads on the next user-run full library scan. Preserve unrelated comparisons and cached data; these mutations must not start or queue a full library scan. This replaces the earlier rule that mapping changes only mark comparisons pending until the next scan. Disable Manual Match mutation controls during a scan and reject mapping saves, deletes, and bulk deletes through the API while a scan is active, including requests from an already-open manager. Ownership corrections were retired by #30; later Manual Match member state, such as Report Missing, follows this same policy.

Persist each affected show's obligation to download fresh applicable TMDB and TVDB data separately from whether its cached comparison is up to date. This mandatory next-scan refresh overrides ordinary same-day reuse for affected shows. A cached recheck performs no Plex enumeration or provider catalogue downloads, does not consume the refresh obligation, and does not advance provider successful-download timestamps, the preceding-completed-full-scan baseline, provider verification positions, or the daily completed-full-scan count. Refresh obligations survive restarts and failed downloads and clear independently per provider only after the required download succeeds. If saved comparison inputs are missing or incomplete, preserve available last-good results and expose a Coverage Issue rather than claiming an empty catalogue or starting a full scan.

Track each show's last successful catalogue download separately for TMDB and TVDB. Reusing data or rerunning a comparison does not reset that timestamp. Provider data older than 60 elapsed days must be refreshed during a scan. Explicitly clearing a show's cache forces fresh provider downloads for that show on its next scan.

Keep catalogue age separate from TMDB verification recovery. Use TMDB's own provider verification position to determine the interval requiring verification. If its change feed cannot cover that interval, recover verification by refreshing the affected TMDB catalogues while preserving successful recovery downloads and outstanding obligations. This replaces the blanket TMDB refresh triggered by a missing full-scan baseline or a previous full scan older than 14 days: the implemented 14-day change-feed window constrains verification recovery, not catalogue age. An unrelated provider failure must not trigger TMDB recovery. This verification gap alone does not force TVDB refreshes.

Isolate failures to the affected provider and shows. A failed lookup retains its retry obligation and visible issue, while successfully downloaded catalogues remain eligible for normal freshness-based reuse. An unrelated unresolved issue must not force otherwise reusable TMDB or TVDB catalogues to download again. A completed full scan establishes recent scan activity even when individual checks fail. Track this activity separately from independent TMDB and TVDB provider verification positions: a failed provider change check retains that provider's previous position so its next check covers the missed interval; the other provider can advance independently. Preserve durable refresh obligations for identified changes whose downloads fail.

Continue provider change detection. For TMDB, a show flagged as changed may reuse a catalogue successfully downloaded on the same UTC date. This deliberately allows a later correction that day to wait until a subsequent day's scan. TVDB retains timestamp-based change checks independently. Persist completed full Plex scan counts per UTC day across restarts. On scans 5, 10, and so on, bypass TMDB's same-day reuse for library shows in that day's TMDB change list; do not force TVDB refreshes or refresh unchanged TMDB shows merely because the count was reached. A full scan counts when it obtains the complete library inventory and finishes processing the library, including when isolated download, comparison, or provider verification issues remain. Interrupted scans, scans with incomplete library inventory, single-show scans, and cached rechecks do not advance the count or completed-full-scan baseline. This replaces the previous clean-scan counting boundary: unresolved issues must not indefinitely prevent the periodic TMDB refresh safeguard from running.

When a change check fails, retain available saved data, visibly mark freshness as unverified, and retry on the next sync. Shows without saved data still require downloads. Mandatory age-based refreshes take precedence over failed change checks and attempt the provider download anyway. If that download fails, retain the last good data, mark freshness as unverified, leave the successful-download timestamp unchanged, and retry on the next scan.

Recovery from a missing verification baseline preserves progress: catalogues successfully refreshed during recovery remain reusable, while outstanding verification and download work is retained and retried. Already successful downloads, including those made before an upgrade that repairs baseline tracking, must not be repeated solely because unrelated recovery work remains unresolved. If the TMDB change feed needed by a fifth-scan safeguard fails, count the completed full scan but retain the safeguard as durable pending work. Retry it on the next full scan that can retrieve the required change list, preserve it across restarts, and keep the verification failure visible until resolved.

Pending fifth-scan safeguards also survive UTC midnight. The new day's completed-full-scan count starts independently, while the pending work retains its original verification interval and covers the missed changes. If that interval is no longer available from the change feed, satisfy it through TMDB verification recovery. Resetting the daily count must never discard unfinished verification work.

Record structured current Coverage Issues for comparison, inventory, provider verification, and download failures, including unverified catalogue freshness and failed refreshes for shows without Manual Matches. Retain provider/operation, readable reason, and known show/episode identities, with library-wide scope when a show cannot be identified. The Coverage Issues report and warning use this same issue state; resolving a cause clears the corresponding issue. Capture diagnostic context when failures occur rather than deriving it solely from a global pending flag.

This replaces library-wide provider fetching caused solely by the existence or revision of manual mappings. Independent provider catalogues require additional persisted data, but preserve the distinction between changes to provider descriptions and changes to local comparison inputs. No new per-show refresh action is planned.

## Delivery boundary

Issue #14 owns the shared backend: provider catalogue persistence and freshness, saved library/comparison inputs, one comparison engine used by full scans and local cached rechecks, affected-show invalidation, durable next-scan refresh obligations, active-scan mutation protection, and structured diagnostic state. Issue #15 depends on #14 and owns the Manual Matches and Coverage Issues reports, report navigation, Matching Episodes dialog, and their integration with those backend operations. It must not introduce a second comparator, cache policy, refresh queue, or diagnostic store. The accepted joint review replaces the original deferred-comparison wording in #14; both tickets now use immediate cached rechecks followed by mandatory affected-show provider downloads on the next user-run full scan.
